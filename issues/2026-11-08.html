START THIS MONTHgreen · pure software · no capital · you are the user: you build with Claude Code and then have nowhere good to put the result

You can build software in a weekend now — and still have nowhere to put it

The problem
Agents made it trivial to build software that will only ever have one or a handful of users — a tool for your team, a tracker for your own workflow. Deploying and sharing it is still as hard as it was in 2015. AWS and Azure were designed for software that scales to millions, and that complexity is now the bottleneck: auth, permissions for arbitrary user-written code, and — the part everyone underestimates — letting a non-technical person run your code without it becoming a security incident.
Who says it's hard
Y Combinator carried this as “A Cloud for Small Software” in its RFS, and the wire keeps re-proving it. This morning two items framed the whole problem by accident: a 444-pt HN post on running a homelab on a $10 USB stick (people are so starved for a place to run their own small software they are repurposing Android dongles), and the day's security headline (§1) — Claude Code leaking secrets into 1,122 public repos — which is partly a story about people with nowhere safe to put the thing they just built.
Why it's still open
The hard parts are not the hosting. They are auth and permissions for arbitrary user-written code, per-person environment customisation, and sharing executable code with someone non-technical safely. The platforms that try (see §8's Coolify, §4's one-VM-per-project tools) mostly solve step one and leave the last mile — “give this URL to my client and let them log in” — to you.
Who's already trying
Vercel, Replit, Val Town, Cloudflare Workers, Deno Deploy on the hosted side; Coolify and Dokploy on the self-host side. All aimed at developers who already know what a container is. Nobody owns the bottom: the person who built one thing with an agent and just wants it live, with a login, for five people.
Your angle
You are the user in its cheapest form — you build with Claude Code and then stall at “now what.” That is the unfair advantage the RFS is describing: you feel the gap the moment you close the laptop. §6 turns the first inch of this into a one-afternoon exercise, and §8 hands you the open-source platform to build the ugly version on top of.
Research path
  1. Build the ugliest possible version for yourself first: one command that takes a Claude Code project and gives you back a URL with a login. Use Coolify (§8) as the engine so you are only solving the last mile.
  2. Read Val Town's engineering writeups on sandboxing user-written code — they have hit every wall you will hit, in public.
  3. Then ask ten people in your hostel who build things where their projects currently live. The honest answer is “localhost,” and that answer is the market.

Claude Code's “Don't Ask Again” wrote real passwords into 1,122 public GitHub repos

1,122 public repos with a live secret in .claude/settings.local.json · 104,185 copies scanned · 1,379 credentials on default branches, 2,539 once you count forks, deleted history and chat logs · found by Apiiro · The Hacker News · Apiiro · HN 262 pts

What happened
When Claude Code asks permission to run a command and you click “Yes, and don't ask again,” it saves the full approved command to .claude/settings.local.json in your project. If that command contained a real database password, API key or token — because you pasted it inline — the secret is now written to a file, and that file gets committed and pushed to GitHub like any other. Apiiro scanned 104,185 public copies of it and found 1,122 (~1.1%) holding at least one live secret.
The tech
The breakdown is 379 database passwords, 43 SSH logins, 42 Git/npm tokens, 23 AWS keys on default branches. Older deleted versions add 734 more across 509 repos; forks spread them further. The sharp finding: of 16 coding agents whose docs Apiiro compared, Claude Code is the only one that saves the full approved command to a project file by default. The design choice — make approvals persistent and legible — is also the leak.
Why it matters
This is the §0-green and the agent-provenance problem in one incident: software built fast, by people running agents on machines that hold their keys, with no habit yet for where secrets live. It is not an exotic exploit. It is the default button, the default file, and git push. Which means the fix is a habit, not a product — and habits are exactly what a whole generation of new builders hasn't formed.
The bear case
For Anthropic, this is embarrassing but bounded: the file is gitignored in recent setups, and the real failure is users pasting secrets inline rather than using env vars. For you, there is no bear case — only a two-minute check you should run today (§6).
What it means
Three moves. First, defensive and immediate: run the §6 scan on every repo you own before you read further — you build with Claude Code, so you are in the exact population this hit. Second, read it as the clearest possible proof of the §0-green thesis: the hard part of personal software is not building it, it is handling it safely afterward, and nobody has made that easy for non-experts. Third, note the product-shaped gap underneath — a dead-simple “did I just commit a secret?” guardrail for the agent-coding crowd, which §4's CloneGuard-style tools gesture at but none owns for this audience.
Your §0 amber, funded · a US-eligible deep-tech lane with government money behind it

The Pentagon is lending a 12-year-old plasma startup $250M to take battery materials back from China

$250M conditional DoD loan · target 6K Energy (North Andover, MA) · founded 2007 as Amastan, renamed 2019 · new cathode-materials factory in Tennessee · prior: a $50M DOE grant (2023) cancelled in 2025 · TechCrunch · MIT News

What they do
6K makes cathode active material — the single most expensive, most China-dependent component in a lithium battery — using a microwave-plasma process it calls UniMelt (“uniform melt state”). It heats metals into a plasma and deposits them directly, collapsing a conventional multi-day, multi-step chemical plant into seconds and far less waste. The $250M builds a Tennessee factory to make LFP cathode domestically.
The tech
The hard part is that cathode production is normally a dirty, slow, water-and-solvent-heavy chemical process, and almost all of it happens in China. 6K's bet is that a plasma reactor does the same job faster, cleaner and on US soil — which is only valuable because the supply chain is a national-security problem, not just a cost one. That is why the lender is the Pentagon, not a bank.
The founders
The unfair advantage is one person's lab. Kamal Hadidi spent 13 years (1994–2007) at MIT's Plasma Science and Fusion Center developing microwave plasmas for hydrogen, fuel reforming and nanomaterials, then spun his own technique out as Amastan in 2007. CEO Aaron Bent (ex-GMZ Energy) runs the commercial side. This is the purest form of the pattern worth internalising: a founder with unusual access to a hard technology — here, a decade inside one of the few labs on earth doing this — who then spent fifteen more years turning it into a factory.
Where the idea came from
Hadidi's MIT years gave him first-hand sight of what microwave plasma could make that conventional chemistry could not. The company is the long merge of that lab access with a market that only recently became urgent: once “made in China” became a liability for batteries, a cleaner domestic process stopped being a science project and became a Pentagon line item.
The bear case
Twelve years in and the factory still isn't built: the original 2024 opening slipped, the 2023 DOE grant was cancelled in 2025, and the company had to re-apply for support. Deep-tech manufacturing is brutally slow and capital-hungry, and a conditional loan is not a cheque cleared. Plasma-made cathode also has to beat Chinese LFP on price, not just provenance — and §9's sodium-ion news is a reminder the chemistry under it can shift.
What it means
This is your §0-amber lane with the money turned on, and it carries two lessons you can act on. First, the door: deep-tech manufacturing re-shoring is a US-government priority with federal financing behind it, and you are eligible for that world when most of your peers are not — read 6K's and the DoD's manufacturing-innovation careers pages as a map of who's hiring. Second, the model: Hadidi is the clearest case study of the only durable startup origin — own a hard thing almost nobody else can do, then wait for the world to need it. Your version is the tiltrotor sub-system you understand better than anyone in your cohort.

The Remake

one evidenced candidate · never more
Same tool, one audience — the proofing app built only for custom-print merchants

A Shopify proof-approval app for print-on-demand sellers, where “which version did they approve?” can never happen

The incumbent
The incumbent is mostly email and DMs — and, for the few who graduate off it, generic proofing tools like Approval Studio Integration on the Shopify App Store, which is built for design agencies broadly, not for a custom-apparel store taking personalised orders through Printful or Printify. The default workflow for most custom-print merchants is a thread of messages and attachments with no system of record.
The complaint
A custom-order merchant, in their own words on the Shopify forum: “Messages can become difficult to track, especially when there have been several revisions, and there can sometimes be confusion later about which version was actually approved.” (Shopify Community thread.) It is not a one-off: this morning's r/shopify carried the same question again — “How Do You Handle Custom T-Shirt Design Approvals Before Production?” The pain is a disputed order: the customer swears they approved a different version, and the merchant has no timestamped proof, so they eat the reprint.
Which remake
Same tool, one audience. Don't build a general proofing suite — build the one that knows what a print order is. It attaches to the Shopify order, shows the customer the exact mockup, captures a one-click, timestamped “I approve this version,” locks the file, and writes an immutable approval record on the order itself. The narrowness is the product: copy, defaults and integrations (Printful/Printify) that make a custom-apparel seller feel the app was built for them, because it was.
The buyer
Shopify merchants selling personalised or custom-print products — apparel, mugs, signage, invitations. They already lose money on reprints and chargebacks from approval disputes, and the ones who've felt it already pay for proofing tools, so budget is proven. Distribution is the Shopify App Store, where they shop with a company card and the charge rides on their Shopify invoice.
Why him
The whole product is a design-and-trust artifact, which is your edge: the customer-facing approval screen has to look reassuring enough that a buyer clicks “approve” with confidence, and most B2B proofing tools look like a tax form. A filmmaker's eye on the one screen that matters is a real moat here, not a nicety. You also feel the buyer's exact anxiety — shipping something you're not sure was signed off is the same dread as §1's “did I just commit a secret?”
First step
Today, don't build — interview. Spin up a free Shopify development store, install Approval Studio and one POD app (Printful), and run yourself through a custom order as both merchant and customer. Then DM five custom-apparel sellers from the two linked threads and ask one question: “what does an approval dispute cost you, in reprints, per month?” That number is your pricing. (Kill-filter check: useful on first install (the next custom order gets a clean approval record); buyer = user with proven budget; runs unattended once wired to the order flow; not ad-supported consumer; and three named payers are describing the exact pain in the linked threads. The trap — “a full creative-agency proofing platform” — fails the one-audience rule: it becomes Approval Studio again, and loses the reason a t-shirt seller would pick you.)

Skill

day 30

Scan every repo you own for a leaked secret — in the next ten minutes, before you read on

~10–30 min · free · produces: certainty that you are not one of the 1,122, plus a reusable guardrail against ever becoming one

Today's §1 lead is that Claude Code's “Don't Ask Again” wrote real passwords into 1,122 public repos, and you build with Claude Code, so this is not abstract. The fix is two tools and a habit. Install gitleaks (one binary) and run gitleaks detect inside each repo you own — it scans not just the current files but your whole git history, which is where a deleted-but-committed secret still lives. For a second opinion, point TruffleHog at your GitHub account; it verifies whether a found key is still live, which is the difference between “clean up later” and “rotate this now.”

Two things come out of a single afternoon. One, you'll know for certain whether anything of yours is exposed — and if it is, the move is rotate the key first, scrub history second, never the reverse. Two, you'll have felt the real shape of the §0-green and §1 problem from the inside: capturing what an agent or a person committed is easy; knowing which of it is dangerous, and tying it back to who did it and whether it's still exploitable, is the hard, valuable part. Wire gitleaks into a pre-commit hook and you've built the smallest honest version of the guardrail nobody ships for the vibe-coding crowd — the one §1 says is a product-shaped hole.

Free resources: gitleaks and TruffleHog (both free, both one command), and GitHub's own secret-scanning docs for how to turn on push protection so the next leak is blocked before it happens.

That is a skill you've told me you want, and most founders die for lack of it, not for lack of code. Fourteen hours is a real cost; it is also the highest-leverage fourteen hours in this whole canon for someone who wants to found a company and not just build a product.

The Wildcard

deliberately not curated to your tastes

The point of this section is to find interests you don't know you have, so it's picked for strangeness and range, never usefulness. Today: Dürer's monument to the peasants he watched get slaughtered, floods read as omens in 17th-century Britain, a hawk that ate so many chickens it couldn't fly, a gold coin from a shipwreck, a rare strike inside the AI supply chain, a book about what writing did to the human mind, and a billion years of Earth's history that simply went missing.

  • Dürer's monument to the vanquished peasants (1525) — after the German Peasants' War, Dürer sketched a victory column topped not with a hero but with a defeated peasant, slumped and stabbed in the back. A great artist designing a monument that quietly mourns the losing side — ambiguous, and still argued over 500 years later.
  • Floods and foreboding in 17th-century Britain — before weather was data, a storm or a flood was a message: divine, political, an omen to be read. A window into a whole cognition where nature was trying to tell you something — and a reminder of how recently we stopped thinking that way.
  • The hawk that ate itself grounded — a wild hawk feasted on a neighbourhood's backyard chickens until it was too fat to take off. Funny, slightly grim, and a tidy little parable about abundance and consequence, feathers attached.
  • A coin from the Ship of Gold — 99% Invisible on a single gold coin recovered from the SS Central America, lost in 1857 with tons of Gold Rush bullion and later salvaged a mile deep. An object as a knot of greed, engineering and history — exactly the kind of thing that rewards a designer's attention.
  • A rare strike in Taiwan, beneath the AI rush — Rest of World on labour unrest in the island that makes the world's chips, as record AI profits flow past the people on the line. The human underside of the supply chain every other story on this page depends on.
  • What writing did to the human mind — a review of Walter Ong's Orality and Literacy, on how the shift from spoken to written culture rewired how people think, remember and argue. Strange and load-bearing: it makes you notice that a technology for words reshaped cognition itself — which is not a neutral thing to be reading in 2026.
  • How Earth lost a billion years of its history — across much of the planet, more than a billion years of rock is simply gone from the record — the “Great Unconformity.” Geologists are still arguing about what erased it. A missing chapter the size of a quarter of Earth's life, hiding in plain sight in every canyon wall.

1 free resource worth your time

Coolify — the free, open-source answer to “where does my Claude Code project actually live?”

free · open-source, self-hostable · the engine to build today's §0-green on top of · coolify.io

Coolify is a free, open-source, self-hostable platform that gives you Heroku/Netlify/Vercel-style deploys on a server you control — push a repo, get a running app with a URL, HTTPS, databases and backups, no per-seat cloud bill. It belongs in today's issue because it's the cheapest honest answer to the §0-green problem: the thing you built with an agent needs somewhere to live that isn't localhost and isn't a $2,000/mo AWS maze. Point it at a $5 VPS (or the $10 OpenStick from §4, if you're feeling it) and you have a personal cloud by dinner. Read it two ways: as a tool you'll actually use this week, and as a teardown — Coolify solves hosting and HTTPS cleanly but still leaves the hard last mile (auth, and safely sharing with a non-technical person) to you. That remaining gap is precisely the §0-green opening. Spend an evening deploying one of your own projects on it; you'll come out with a live URL and a much sharper sense of what the real unsolved part is.
